# Signing

> Create, fetch, share, inspect, and use signing assets without committing private keys.

Apple code signing has four separate pieces:

1. A bundle ID identifies each app or embedded target. Capabilities on the bundle ID must match the app's entitlements.
2. A certificate is the public half of a signing identity. App Store Connect can create and return the certificate, but it cannot return the private key.
3. A provisioning profile binds a bundle ID, certificate, capabilities, and, for development or release testing, registered devices.
4. The machine running Xcode needs the matching private key and the right profile at the same time.

`asc` manages each piece and can store a usable private identity in an encrypted Git repository. It never invents or downloads a missing private key.

## Choose the right command

| Goal | Command |
| --- | --- |
| Download an existing certificate and profile | `asc signing fetch` |
| Create a profile when one is missing, then download it | `asc signing fetch --create-missing` |
| Encrypt one app's signing assets and local private identity in Git | `asc signing sync push --bundle-id ...` |
| Sync one shared identity across an app and its embedded targets | `asc signing sync push --targets-file ...` |
| Decrypt signing assets on another machine or CI worker | `asc signing sync pull` |
| Plan profiles for every target in an iOS archive and an exact device set | `asc signing reconcile plan` |
| Apply an approved reconciliation plan | `asc signing reconcile apply --confirm` |
| Run one release-testing command with a temporary keychain | `asc signing run` |

Use `fetch` when the matching private key already exists on the machine. Use `sync` when a team or CI worker needs the private identity too. Use `reconcile` for multi-target, registered-device release testing where one stale or incomplete profile can break the whole export.

## Before you start

Authenticate with an App Store Connect API key that can read signing resources and perform any requested creation:

```bash  theme={null}
asc auth status
asc certificates list --output table
asc profiles list --output table
asc bundle-ids list --output table
```

For encrypted sync, you also need:

- a private Git repository that the current Git credentials can clone and push;
- a generated, high-entropy repository password stored in a private file or secret manager;
- a PKCS#12 (`.p12`) identity, or the RSA/EC private key that created the certificate request.

Prefer an SSH key or Git credential helper for repository authentication. Do not embed an access token in `--repo`; command lines can be retained in shell history, process listings, CI logs, and job metadata.

Private input files must be regular files, must not be symlinks, and must not be accessible by group or other users. Fix their permissions before running a signing command:

```bash  theme={null}
chmod 600 \
  ~/.config/asc/signing-sync-password \
  ./distribution.p12 \
  ./distribution-p12-password
```

Keep decrypted outputs and secrets out of source control:

```gitignore
.asc/secrets/
.asc/signing/
.asc/distribution/signing/
```

## Set up the bundle ID and capabilities

Find an existing explicit bundle ID:

```bash  theme={null}
asc bundle-ids list \
  --identifier com.example.app \
  --output table
```

Create it when it does not exist:

```bash  theme={null}
asc bundle-ids create \
  --identifier com.example.app \
  --name "Example" \
  --platform IOS
```

Check capabilities before creating profiles. A profile takes a snapshot of the bundle ID's capability state, so one created before a capability change can be unusable.

```bash  theme={null}
asc bundle-ids capabilities list \
  --bundle BUNDLE_ID \
  --output table

asc bundle-ids capabilities add \
  --bundle BUNDLE_ID \
  --capability PUSH_NOTIFICATIONS
```

Capabilities with settings accept a structure-validated JSON array. Field names and value types must match Apple's request schema:

```bash  theme={null}
asc bundle-ids capabilities add \
  --bundle BUNDLE_ID \
  --capability ICLOUD \
  --settings '[{"key":"ICLOUD_VERSION","options":[{"key":"XCODE_6","enabled":true}]}]'
```

Create a new profile after changing capabilities; App Store Connect profiles are immutable.

## Fetch public signing files

`asc signing fetch` resolves the bundle ID, selects an active profile and its active certificates, then writes the `.mobileprovision` and `.cer` files to the output directory.

For App Store distribution:

```bash  theme={null}
asc signing fetch \
  --app APP_ID \
  --bundle-id com.example.app \
  --profile-type IOS_APP_STORE \
  --output .asc/signing/app-store \
  --format json \
  --pretty
```

`--app` is optional, but when supplied it verifies that the App Store Connect app record uses the requested bundle identifier.

To create a missing profile:

```bash  theme={null}
asc signing fetch \
  --bundle-id com.example.app \
  --profile-type IOS_APP_STORE \
  --create-missing \
  --output .asc/signing/app-store
```

For development or ad hoc distribution, profile creation needs device resource IDs:

```bash  theme={null}
asc devices list --platform IOS --output table

asc signing fetch \
  --bundle-id com.example.app \
  --profile-type IOS_APP_ADHOC \
  --device "DEVICE_ID_1,DEVICE_ID_2" \
  --create-missing \
  --output .asc/signing/release-testing
```

`--device` only affects profiles created by that invocation. During 4.x, passing it without `--create-missing` prints a deprecation warning and ignores the device IDs; 5.0.0 will reject that combination.

The command does not overwrite output files. This prevents a failed write from silently replacing a known profile or certificate.

### Common profile types

| Profile type | Use | Inferred certificate type | Devices when creating |
| --- | --- | --- | --- |
| `IOS_APP_STORE` | iOS App Store and TestFlight | iOS distribution | No |
| `IOS_APP_DEVELOPMENT` | iOS development | iOS development | Yes |
| `IOS_APP_ADHOC` | iOS release testing on registered devices | iOS distribution | Yes |
| `TVOS_APP_STORE` | tvOS App Store | iOS distribution | No |
| `TVOS_APP_DEVELOPMENT` | tvOS development | iOS development | Yes |
| `TVOS_APP_ADHOC` | tvOS release testing | iOS distribution | Yes |
| `MAC_APP_STORE` | Mac App Store | Mac distribution | No |
| `MAC_APP_DEVELOPMENT` | macOS development | Mac development | Yes |
| `MAC_APP_DIRECT` | Developer ID distribution | Developer ID Application | No |
| `MAC_CATALYST_APP_STORE` | Mac Catalyst App Store | Mac distribution | No |
| `MAC_CATALYST_APP_DEVELOPMENT` | Mac Catalyst development | Mac development | Yes |

Use `--certificate-type` only when the inferred type is not the one you need.

## Create a certificate without losing its private key

If no suitable certificate exists, generate the private key and certificate signing request locally while creating the App Store Connect certificate:

```bash  theme={null}
mkdir -p .asc/signing .asc/secrets
chmod 700 .asc/signing .asc/secrets

asc certificates create \
  --certificate-type IOS_DISTRIBUTION \
  --generate-csr \
  --key-out .asc/secrets/distribution.key \
  --csr-out .asc/signing/distribution.csr \
  --output json \
  --pretty > .asc/signing/distribution-certificate.json
```

The private key stays at `--key-out`; the API response contains only the public certificate. Keep the key private and back it up through encrypted sync before deleting the bootstrap copy.

To pair the generated key with `signing sync push`, calculate the SHA-256 fingerprint of the returned certificate:

```bash  theme={null}
CERTIFICATE_SHA256="$(
  jq -r '.data.attributes.certificateContent' \
    .asc/signing/distribution-certificate.json \
  | openssl base64 -d -A \
  | openssl x509 -inform DER -outform DER \
  | shasum -a 256 \
  | awk '{print toupper($1)}'
)"
```

Do not print the private key or store it in shell history. The certificate fingerprint is public metadata.

## Share a usable signing identity

`signing sync push` fetches the chosen certificate and profile, verifies the local private identity against them, encrypts the assets, and publishes one Git commit. It works in a temporary clone and removes that clone after the run.

### Push a PKCS#12 identity

```bash  theme={null}
asc signing sync push \
  --bundle-id com.example.app \
  --profile-type IOS_APP_STORE \
  --repo git@github.com:team/signing.git \
  --password-file ~/.config/asc/signing-sync-password \
  --identity .asc/secrets/distribution.p12 \
  --identity-password-file .asc/secrets/distribution-p12-password \
  --output json \
  --pretty
```

An unprotected PKCS#12 does not need `--identity-password-file`. If the file contains more than one identity, select the intended certificate with `--identity-sha256`.

### Push the private key created with the CSR

```bash  theme={null}
asc signing sync push \
  --bundle-id com.example.app \
  --profile-type IOS_APP_STORE \
  --repo git@github.com:team/signing.git \
  --password-file ~/.config/asc/signing-sync-password \
  --private-key .asc/secrets/distribution.key \
  --identity-sha256 "$CERTIFICATE_SHA256" \
  --create-missing \
  --output json \
  --pretty
```

`--private-key` accepts RSA or EC PEM keys and always requires the certificate fingerprint. The CLI checks the private key's public half against the selected active, unexpired App Store Connect certificate and the certificate embedded in the profile.

Private identity sync does not yet support `MAC_APP_DIRECT` or `MAC_CATALYST_APP_DIRECT`. Certificate-and-profile-only sync still works for those types when `--identity` and `--private-key` are omitted.

### Sync an app and embedded targets together

Use `--targets-file` for an app, widgets, extensions, App Clips, or other targets that share one profile type and identity. It is mutually exclusive with `--bundle-id`; the remaining push flags apply to every target.

```json
{
  "schemaVersion": 1,
  "targets": [
    {"bundleId": "com.example.app"},
    {"bundleId": "com.example.app.widget"}
  ]
}
```

The manifest accepts 1 to 32 unique bundle identifiers. It must be a command-root-relative regular JSON file smaller than 64 KiB; absolute paths, symlinks, `..` escapes, unknown fields, duplicate IDs, path characters, and control or bidi characters are rejected before passwords, authentication, network requests, or Git work.

```bash  theme={null}
asc signing sync push \
  --targets-file ./signing-targets.json \
  --profile-type IOS_APP_STORE \
  --repo git@github.com:team/signing.git \
  --password-file ~/.config/asc/signing-sync-password \
  --identity .asc/secrets/distribution.p12 \
  --identity-password-file .asc/secrets/distribution-p12-password \
  --create-missing \
  --output json \
  --pretty
```

Targets are processed in deterministic order. Shared certificates and identities are stored once, profiles use bundle-scoped paths, and the repository gets at most one commit and push. An unchanged rerun creates neither.

`--create-missing` can create App Store Connect profiles before the final Git push. If a later target or repository publication fails, those immutable profiles may remain; the error reports that boundary. Rerun after fixing the failure or inspect the profiles before deciding whether cleanup is appropriate.

Batch JSON includes `bundleIds` and one `targets` result per bundle. Each result states its profile path, whether the profile was created, and the files stored for that target.

### Pull on another machine

```bash  theme={null}
mkdir -p .asc/signing
chmod 700 .asc/signing

asc signing sync pull \
  --repo git@github.com:team/signing.git \
  --password-file ~/.config/asc/signing-sync-password \
  --output-dir .asc/signing/pulled \
  --output json \
  --pretty > .asc/signing/pull-result.json

jq -r '.sensitiveFiles[]?' .asc/signing/pull-result.json
```

Pulled private identities appear in `sensitiveFiles`; ordinary certificate and profile paths appear in `files`. New files use mode `0600`, and the command refuses unsafe identity envelopes, oversized repositories, path escapes, and metadata that does not match the encrypted artifact.

The normalized PKCS#12 is protected by the same sync password. A pull that reports `identityPresent: false` contains certificates and profiles only and cannot sign an app by itself.

Use `--password-file` for local work. In a secret-managed CI environment, `ASC_SIGNING_SYNC_PASSWORD` is also supported. The inline `--password` flag and `ASC_MATCH_PASSWORD` are deprecated during 4.x and will be rejected in 5.0.0.

### Current sync scope

The encrypted store currently uses Git. Push applies one profile configuration and one identity across its selected targets; it does not accept per-target profile types or device sets. Pull decrypts the whole repository rather than selecting individual apps. Password rotation, certificate renewal, persistent keychain import, and stale-asset deletion remain explicit operator work.

## CI example

The example below writes the repository password to a runner-private file without enabling shell tracing, pulls the encrypted assets, and removes the password file after use. Do not upload `.asc/signing/pulled` as a workflow artifact.

```yaml  theme={null}
- name: Pull signing assets
  shell: bash
  env:
    SIGNING_SYNC_PASSWORD: ${{ secrets.SIGNING_SYNC_PASSWORD }}
  run: |
    set +x
    umask 077
    password_file="$RUNNER_TEMP/asc-signing-password"
    trap 'rm -f "$password_file"' EXIT
    printf '%s' "$SIGNING_SYNC_PASSWORD" > "$password_file"
    mkdir -p .asc/signing
    chmod 700 .asc/signing

    asc signing sync pull \
      --repo git@github.com:team/signing.git \
      --password-file "$password_file" \
      --output-dir .asc/signing/pulled \
      --output json > .asc/signing/pull-result.json
```

For an App Store export, install the pulled provisioning profiles and import the pulled identity into a job-scoped macOS keychain using your CI's keychain setup. `asc profiles local install` can install each profile safely:

```bash  theme={null}
asc profiles local install \
  --path .asc/signing/pulled/profiles/PROFILE.mobileprovision \
  --output json
```

Then archive and export with manual signing when the project requires an exact local identity/profile match:

```bash  theme={null}
asc xcode archive \
  --workspace Example.xcworkspace \
  --scheme Example \
  --archive-path .asc/artifacts/Example.xcarchive

asc xcode export \
  --archive-path .asc/artifacts/Example.xcarchive \
  --ipa-path .asc/artifacts/Example.ipa \
  --signing-style manual \
  --team-id TEAM_ID
```

Manual export inspects the archive and matches locally installed profiles for the main app and embedded targets. An explicit `--export-options` file is authoritative and cannot be combined with `--signing-style`, `--team-id`, or `--method`.

## Reconcile registered-device profiles for an archive

`signing reconcile` is an iOS, macOS-hosted workflow for ad hoc release testing. It inspects the signed entitlements of the main app and embedded app, extension, Watch, and App Clip targets inside an `.xcarchive`.

Create a protected devices file:

```json
{
  "schemaVersion": 1,
  "devices": [
    {
      "name": "QA iPhone",
      "udid": "DEVICE_UDID",
      "platform": "IOS"
    }
  ]
}
```

```bash  theme={null}
chmod 600 .asc/distribution/devices.json

asc signing reconcile plan \
  --archive-path .asc/artifacts/Example.xcarchive \
  --devices-file .asc/distribution/devices.json \
  --minimum-validity-days 14 \
  --state-dir .asc/distribution/signing \
  --output json \
  --pretty
```

Planning makes no App Store Connect mutations. It writes a mode-`0600` `plan.json`; a blocked plan still succeeds with `ready: false` so automation can inspect its blockers. Raw UDIDs do not appear in the plan or normal command output.

When more than one active iOS distribution certificate is eligible, select one resource ID explicitly:

```bash  theme={null}
asc signing reconcile plan \
  --archive-path .asc/artifacts/Example.xcarchive \
  --devices-file .asc/distribution/devices.json \
  --certificate CERTIFICATE_ID \
  --output json
```

Review the plan, then apply that exact artifact:

```bash  theme={null}
asc signing reconcile apply \
  --plan .asc/distribution/signing/plan.json \
  --confirm \
  --output json \
  --pretty
```

Apply rechecks the archive, device input, plan hash, and remote preconditions before each action. It can register missing devices, create baseline explicit bundle IDs, and create successor ad hoc profiles. It never deletes or updates profiles, creates certificates, changes capabilities, or broadens the requested device set. A partial mode-`0600` receipt records completed work so the same plan can be retried safely.

Value-specific entitlements such as App Groups, Apple Pay merchant IDs, Network Extensions, and Wallet pass identifiers can block a plan when their remote settings cannot be proved. Configure those capabilities first; do not treat a blocked plan as permission to guess.

## Run one command with a temporary signing identity

`asc signing run` is macOS-only and currently accepts iOS release-testing profiles: the profile must contain registered devices, must not allow debugging, and must not be an enterprise or App Store profile.

It validates the PKCS#12, private key, certificate, team, signed profile, expiration, and embedded certificate before changing local signing state. It then creates a private temporary keychain, installs the profile only for the child process, executes the argv after `--` without a shell, and removes ASC-owned temporary state afterward.

```bash  theme={null}
signing_command=(
  asc xcode export
  --archive-path .asc/artifacts/Example.xcarchive
  --ipa-path .asc/artifacts/Example.ipa
  --method release-testing
  --signing-style manual
  --team-id TEAM_ID
)

asc signing run \
  --identity .asc/signing/pulled/identities/distribution/IDENTITY.p12 \
  --identity-password-file ~/.config/asc/signing-sync-password \
  --profile .asc/signing/pulled/profiles/PROFILE.mobileprovision \
  --purpose release-testing \
  --receipt .asc/distribution/signing-run.json \
  -- "${signing_command[@]}"
```

The child owns stdin, stdout, stderr, and its exit code. The optional receipt contains certificate/profile digests, profile UUID, team, bundle ID, child result, and cleanup state; it does not contain credentials, device identifiers, or child arguments.

If a prior run was interrupted, the next run attempts bounded recovery from an ASC-owned crash journal. It refuses journals or files that fail ownership, permission, containment, link-count, or digest checks.

## Inspect and maintain local profiles

Inspect a downloaded profile without installing it:

```bash  theme={null}
asc profiles inspect \
  --path .asc/signing/app-store/PROFILE.mobileprovision \
  --output json \
  --pretty
```

Install by file or App Store Connect resource ID:

```bash  theme={null}
asc profiles local install --path ./PROFILE.mobileprovision
asc profiles local install --id PROFILE_ID
```

List installed profiles and find expired entries:

```bash  theme={null}
asc profiles local list --bundle-id com.example.app --output table
asc profiles local list --expired --output table
```

Preview cleanup before confirming it:

```bash  theme={null}
asc profiles local clean --expired --dry-run
asc profiles local clean --expired --confirm
```

## Rotation and expiry

Profiles cannot be edited. When a device, capability, certificate, or validity requirement changes, create a successor profile and move builds to it. Keep the old profile until every active build path has switched.

For certificate rotation:

1. Create the new certificate from a locally retained private key or a new generated CSR.
2. Create or reconcile profiles that use the new certificate.
3. Push the new identity and verified profiles to the encrypted repository.
4. Pull and test on a clean worker before deactivating the old certificate.

Git history retains encrypted prior assets, so repository access and password rotation deserve the same controls as other signing secrets. Do not commit the decrypted pull directory, password files, raw private keys, or PKCS#12 inputs.

## Troubleshooting

### `bundle ID not found`

Create the bundle ID first, or check the exact identifier with `asc bundle-ids list --identifier ...`. For extensions, create and configure every embedded target's bundle ID separately.

### `no certificates found`

Run `asc certificates list --output table`. If a new certificate is required, use `asc certificates create --generate-csr` so the private key exists locally and can be backed up.

### `no active profile found`

Add `--create-missing` after confirming the bundle ID capabilities. For development or ad hoc profiles, also provide device resource IDs.

### `identity private key does not match`

The local key, App Store Connect certificate, and certificate embedded in the profile are not one identity. Select the correct PKCS#12 identity with `--identity-sha256`, or use the private key that created the certificate request.

### `multiple certificates` or `multiple identities`

Choose the exact certificate. `signing sync push` accepts `--identity-sha256`; `signing reconcile plan` accepts the App Store Connect `--certificate` resource ID.

### Protected file or symlink errors

Move the input to an owner-controlled directory, replace symlinks with regular files, and run `chmod 600 FILE`. The signing commands intentionally reject permissive or ambiguous secret paths.

### `signing run` rejects the profile

Use an iOS ad hoc profile with registered devices and `get-task-allow` disabled. App Store, development, enterprise, macOS, and tvOS profiles are outside the current `release-testing` boundary.

### Reconciliation returns `ready: false`

Read the plan blockers. Common causes include multiple eligible certificates, an entitlement whose capability settings cannot be verified, a team mismatch, an unsupported archive platform, or a mutation count over `--max-mutations`. Planning does not repair those conditions silently.
